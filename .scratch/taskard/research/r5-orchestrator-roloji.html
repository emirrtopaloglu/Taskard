Orchestrator'lar Agentlarını Nasıl Tanımlıyor?

Taskard roloji araştırması · 26 Ağustos 2026 · 9 orchestrator/framework · ~40 kaynak tarandı

Sektörde iki farklı rol felsefesi var: aşama rolleri (implementer–reviewer–tester gibi, işin yaşam döngüsüne göre bölünür) ve stack rolleri (backend, mobil, data… uzmanlık alanına göre bölünür). Olgun sistemler az sayıda aşama rolü + ayrı bir kural/skill katmanıyla çalışıyor; devasa rol katalogları ise daha çok "kütüphane" olarak duruyor. Taskard zaten doğru eksende.

2 · Rol Ekseni: Aşama mı, Stack mi?

Aşama (yaşam-döngüsü) rolleri

  • Plan/spec: BMAD PM+SM, Anthropic initializer/planner, Roo Architect
  • Implement: Taskard implementer, claude-flow coder, MetaGPT Engineer, Roo Code
  • Review: neredeyse hepsi — Taskard reviewer, Devin Review, ChatDev Reviewer, Roo Ask
  • Test/doğrula: BMAD QA, MetaGPT QA Engineer, Anthropic evaluator, claude-flow tester
  • Koordinasyon: Roo Orchestrator, Devin manager, ChatDev CTO

Stack (uzmanlık) rolleri

  • Backend/frontend/mobile: VoltAgent core-dev, claude-flow backend-dev & mobile-dev, sarvottam koleksiyonu
  • Data/ML: data-engineer, ml-developer, database-optimizer (her iki katalogda da var)
  • Güvenlik/DevOps: security-auditor, penetration-tester, cicd-engineer, sre
  • Dil uzmanları: python-pro, go-architect, rust-architect (yalnızca kataloglarda)

Dikkat: stack rolleri yalnızca katalog tipi sistemlerde yoğun; üretim pipeline'larında (Devin, Roo, Anthropic) yok — onlar disiplini rule/skill dosyalarından alıyor.

Uzun, kapsamlı, her şeyi listeleyen. Yeni başlayan için iyi, ama prompt şişmesi riski taşır.

Roo Code (mod)

- slug: debug
  name: 🪲 Debug
  roleDefinition: You are Roo,
  an expert in root cause
  analysis...
  whenToUse: Use for investigating
  bugs, errors, unexpected behavior
  groups:
    - read
    - edit
    - command

whenToUse = orchestrator routing girdisi. Tool gruplarıyla yetki sınırı tek satırda. Taskard'ın description+fro­ntmatter ikilisine en yakın yapı.

Taskard (konvansiyon) — mevcut implementer.md'nin iskeleti

---
name: implementer
description: Brief'teki görevi TDD disipliniyle uygulayan ucuz el...
---

Sen bir lane'in delegate'isin. Brief dışına çıkmak yasaktır.
- TDD: önce failing test, sonra minimal implementasyon
- Başarıyı BEYAN ETME, kanıtla: komut + son 3 satır çıktısı

## Bitirme protokolü
Durum: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
## Dönüş kuralı
Mesaj = pointer, dosya = payload.

Prompt Shelf standardıyla ölçüldüğünde Taskard tanımları zaten sağlam: kısa, done-when'li, sözleşmeli. Eksik tek boyut: description'da tetik koşulu ve kapsam dışı beyanı (Roo'nun whenToUse'unun karşılığı).

5 · Taskard İçin Çıkarımlar

  • Eksen doğru: Üretimde kanıtlanmış tüm sistemler (Devin, Roo, Anthropic harness) aşama rollü; stack rollü kataloglarda kalıyor. backend-developer/data-engineer'ı agent yapma; disiplini brief + skill router'a bırak — sektörün ortak kararı bu.
  • Eksiğin adı whenToUse: Roo'nun orchestrator'a yönlendirme alanı, mehdi.cz'in "tetik koşulu" şablonuyla aynı şey. Üç agent'ın description'ına "ne zaman / ne zaman değil" cümlelerini ekle — routing doğruluğu buradan gelir.
  • qa-tester ekle, ama Roo Debug gibi tanımla: read-mostly + komut yetkisi, end-state doğrulaması, fix'i brief'e yazıp döndürme. BMAD QA + Anthropic evaluator karışımı; Taskard'ın üç kapısının dördüncüsü.
  • Model kalibrasyonunu katalogdan al: reviewer → güçlü model (derin muhakeme kapısı), implementer → orta, ileride eklenecek explorer/doc rolleri → hafif. config.toml'daki rol/model seçimini bu tabloya oturt.
  • Persona Taskard'ın farkı olabilir: BMAD'ın isimli personacıları ("Mary hep Mary") hatırlanabilirlik + tutarlılık getiriyor. Taskard'ın Humanish diliyle uyumlu — roller isimsiz değil, karakterli olabilirdi; en azından reviewer'a "şüpheci ikinci göz" gibi net bir ses ver.
